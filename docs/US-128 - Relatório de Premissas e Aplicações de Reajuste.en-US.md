## [US-128] — Assumptions and Adjustment Applications Report (View, Print, Export)

**Module:** Budgetary — Assumptions / Adjustments
**Epic:** EP48/26 — Budgetary Module
**Priority:** High
**Estimate:** M

**As a** Budget Analyst, Auditor, or Planner authenticated in SGO 2.0,
**I want** to view, query, and export the Contractual Adjustment Assumptions / Applications report by Proposal and Version,
**So that** I can analyze the projected adjustment indexes by analytical account across the contract's validity years, with no possibility of manually editing the displayed data.

### Context and Business Rules

Covers the **read-only** slice of UC04.02 (`docs/4 - Minuta da Especificação do Módulo Orçamentário-V2.docx`, [[modulo_orcamentario_ep48_minuta]]), formalized in Scenarios 1-7 of `docs/CA_UC04.02_Premissas_Reajustes_Rev00.docx` (Rafael Guerra/GIA, reviewed by Fabiano/BA-PO, 2026-08-10). The **write** slice (simulate and apply a batch adjustment, Scenarios 8-14 of the same acceptance criteria document) is **US-129**, deliberately separated — they are different risk natures (query vs. batch financial operation).

Operates as a Reactive View: no data is editable on screen [SHIELDED SOURCE]. Segregates the assumptions into two fixed blocks — "Contracts" and "Partnership (ACT)".

**User decision (2026-08-10) — the "Formula" entity from the document is NOT new, it is the existing Tax Allocation screen:**
- `Formula` (document) = `AliquotaImpostoParametro` (current schema). The `tipoIncidencia` field (`CONTRATO` | `TERMO_DE_PARCERIA` | `AMBOS`) is already exactly the segregation from RN0239 ("Contracts" vs. "Partnership/ACT") — no new enum, no new entity.
- `aliquotaPct` (`Decimal(5,2)`) is the adjustment/index percentage; `dataInicioVigencia`/`dataFimVigencia` is the validity window that feeds RN0225 (the "Realized" status vs. a future percentage).
- `RateioImpostoGrade` (the link between `aliquotaParametroId` + analytical `contaId` + `competencia` + `valorDeclarado` + `aliquotaAplicadaSnapshot`) is already the mechanism for application by account and by reference period — this is the "application" referred to in the UC's title ("Assumptions / **Applications** of Adjustments").
- **There is no schema blocker for this US.** This report is essentially a **new view over data that already exists** (`AliquotaImpostoParametro` + `RateioImpostoGrade`), reorganized into the year-by-year matrix layout requested by the document — not a new domain feature.
- **[ADR-040] Year-by-year validity→grade mapping CLOSED.** Algorithm, per analytical account and per month: (1) among the `AliquotaImpostoParametro` records already linked to that account via `RateioImpostoGrade.aliquotaParametroId`, find the one whose window `[dataInicioVigencia, dataFimVigencia ?? +∞)` covers the month; (2) month `<=` current month → always tagged "Realized", regardless of whether a parameter is found; (3) month `>` current month → the `aliquotaPct` of the parameter found, or "—" if none covers that month (no automatic inheritance between successive adjustments — a conscious decision, see ADR-040 for the rationale and the review trigger).

**Gap still open, not resolved by this decision:**
- **Account level.** The document assumes `ContaAnalitica` is always at Level 7; the current schema (`ContaContabil.nivel`) supports 1-4. This is the same blocker already recorded for the entire Budgetary Module — [[modulo_orcamentario_ep48_minuta]]. Not resolved; the Draft (V2) is not yet the final version according to the user (2026-08-10). This does not prevent designing this US (the report works the same at any tree depth), it only prevents closing out the final coding until the Draft stabilizes.

Applicable business rules (mapped 1:1 from the acceptance criteria document, already using the real schema's terminology):
- **RN0225** — Dynamic Validity Status: a past month displays the "Realized" tag; a future month displays the current `aliquotaPct`. Pure date comparison against the server's current month — SGO 2.0 does not integrate with a real ERP Senior, so "Realized" here is just a read-only label, without fetching an external value.
- **RN0227** — Descriptive field generated by the system, Read-Only.
- **RN0239** — Mandatory segregation into 2 blocks, via `AliquotaImpostoParametro.tipoIncidencia` (`CONTRATO` / `TERMO_DE_PARCERIA`; `AMBOS` appears in both blocks).
- **RN0383** — `[Show Zeroed Accounts (Yes/No)]` filter — analytical accounts with no `RateioImpostoGrade` linked.
- **RN0232** — Synchronous log in `HistoricoOperacao` on every query/print/export with a result (do not log an empty query — Scenario 6).
- **RN0200/RN0398** — Applied-filters panel + timestamp in the footer of exported PDF/XLSX (same pattern already used in `exportarRelatorio.ts`, ADR-037).

### Acceptance Criteria

**Scenario 1 — Standard query, zeroed accounts hidden**
```gherkin
Given the user has read permission on Budgetary > Adjustment Assumptions
And the selected Proposal has analytical accounts with a RateioImpostoGrade linked to an AliquotaImpostoParametro
When the user selects Proposal, Version, keeps [Show Zeroed Accounts] = No, and clicks [Query]
Then the system associates each analytical account with the current AliquotaImpostoParametro(s) (RN0225)
And renders 2 fixed blocks: "Contracts" (tipoIncidencia = CONTRATO) and "Partnership (ACT)" (tipoIncidencia = TERMO_DE_PARCERIA); AMBOS appears in both (RN0239)
And each past-month cell displays the "Realized" tag; a future month displays the aliquotaPct in effect for that period
And accounts with no RateioImpostoGrade linked are hidden
And the query log is recorded in HistoricoOperacao with the applied filters (RN0232)
```

**Scenario 2 — Query with zeroed accounts visible**
```gherkin
Given there are analytical accounts with no RateioImpostoGrade linked in the Proposal
When the user sets [Show Zeroed Accounts] = Yes and clicks [Query]
Then all analytical accounts of the Proposal appear, including those with no allocation (RN0383)
And accounts with no allocation are displayed with "0.00%" in every year column
And the block segregation (Contracts/ACT) still applies regardless of the filter
```

**Scenario 3 — Export XLSX**
```gherkin
Given a query has been performed successfully
When the user clicks [Export]
Then the system generates an XLSX file by reusing exportarParaXLSX (ADR-037, no new library)
And the file header stamps the Partnership Agreement Name + Version (RN0200)
And the footer contains the server's timestamp (RN0398)
And the export log is recorded in HistoricoOperacao
```

**Scenario 4 — Print**
```gherkin
Given a query has been performed successfully
When the user clicks [Print]
Then the system triggers window.print() with a dedicated layout (same print CSS pattern as the Disbursement Schedule, US-122)
And the printed title is "ADJUSTMENT ASSUMPTIONS / APPLICATIONS (%)" + Partnership Agreement Name + " - CONSOLIDATED", with "SCENARIO" tags + Version Number + Issue Date
And the printed footer carries the fixed title "ADJUSTMENT ASSUMPTIONS / APPLICATIONS (%)"
And the print log is recorded in HistoricoOperacao
```

**Scenario 5 — Access without permission**
```gherkin
Given the user's profile does not have read access to this report's Feature
When the user tries to access the tab/route
Then the system blocks access (same usuarioTemFuncionalidade pattern already used throughout the project)
And no data is queried
```

**Scenario 6 — Proposal with no allocations registered**
```gherkin
Given the selected Proposal has no RateioImpostoGrade registered
When the user clicks [Query]
Then the system displays "No adjustment assumption registered for the selected proposal and version."
And the [Print]/[Export] buttons are disabled
And no log is recorded for an empty query
```

**Scenario 7 — Attempt at manual editing (SHIELDED SOURCE)**
```gherkin
Given the matrix is rendered on screen
When the user tries to change any percentage or description cell
Then nothing happens — all fields are strictly Read-Only, with no input whatsoever in the grid (passive blocking by design, no error message)
```

### Dependencies

- **[ADR-040]** defines the only migration for this line of work: widening `AliquotaImpostoParametro.aliquotaPct` from `Decimal(5,2)` to `Decimal(9,4)` (shared with US-129, RNF_PR_004). No additional migration is needed for US-128 on its own.
- **Account-level blocker** (Budgetary Module as a whole) — see [[modulo_orcamentario_ep48_minuta]]. Awaiting the final version of the source document.
- **Implemented without a dedicated `Funcionalidade`** — same pattern already used by the sibling "Disbursement Schedule" tab (US-122): it is a tab within the Proposal's detail view, controlled only by general access to the Proposal/Version, with no per-Feature permission gate. Scenario 5 (access without permission) reflects this pattern — only reinforce it here if the product decides to introduce per-tab access control across the whole app, which does not exist today even for reports already in production.
