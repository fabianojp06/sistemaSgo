UC0 3.00 - Configure Chart of Accounts Structure
Objective
Responsible for two complementary responsibilities: (1) providing the SGO with a central mechanism for importing and synchronizing the corporate Unified Chart of Accounts, fed exclusively via integration with the Senior ERP, keeping the official accounting structure Read-only in the SGO; and (2) allowing the creation and management of SGO-exclusive Account Groupers, which enable creating custom subtotal views over analytical accounts imported from the ERP, without interfering with the official hierarchy. Operates under the "Shielded Origin" and "Error Lock" directives to guarantee structural accounting protection.
Actors involved 	Common User / Budget Analyst / Financial Manager / Auditor / SGO System 
Conditions 
Pre-Conditions 
•	The user must be authenticated with an active administrative or accounting profile.
•	The SeniorIntegrationController communication gateway must be operational and stable with the Senior ERP (for the synchronization flow).
•	The accounting Chart of Accounts must be previously approved and active in the Senior ERP database.
Post-Conditions
•	After synchronization: Unified Chart of Accounts tree updated in the SGO with status "Synchronized." Core fields (Number, Name, Hierarchy) become immutable on screen.
•	Leaf nodes (Level 7) become available for selection in Proposal and Sizing forms.
•	After creating/editing a Grouper: Account Grouper registered and available in reports (Disbursement Schedule, Expense Forecast) as a subtotal line.
•	All operations recorded in the audit trail (HistoricodeOperacoes) (RN_PLA_004).
Scenarios 
Main Flow – Synchronizing the Chart of Accounts with Senior ERP
1.	The administrator user accesses the Unified Chart of Accounts parameters screen;
2.	The system renders the current accounting tree in protected mode and displays the [Synchronize with Senior ERP] action button and the [Account Groupers] panel;
3.	The user clicks [Synchronize with Senior ERP] to trigger the batch update [E1];
4.	The SGO triggers the SeniorIntegrationController, which consumes the external ERP endpoints and brings in the structured payload (RNF_PLA_REQ_001 / RNF_PLA_REQ_002);
5.	The system runs the batch's referential integrity validations [E2] and performs an atomic commit of the synthetic accounts (Levels 1 to 6) and analytical accounts (Level 7) (RNF_PLA_REQ_004);
6.	The screen updates reactively, displaying the new accounts with the "Synchronized" tag and generating a success log in the audit trail (RN_PLA_004).

A1 — Cancel Operation 
•	A1.1.  The user clicks [Cancel] at any step before confirming the synchronization;
•	A1.2.  The system aborts the flow without triggering requests to the ERP and returns to the Chart of Accounts screen in its previous state.

A2 — Create Account Grouper 
•	A2.1.  At step 2 of the main flow, the user clicks [New Grouper] in the Account Groupers panel;
•	A2.2.  The system displays the creation modal form with the fields: [Grouper Name] (required) and [Analytical Accounts] — multiple selector of Level 7 accounts available in the Chart of Accounts imported from the ERP;
•	A2.3.  The user fills in the Name (e.g., "Airfare expenses") and selects the analytical accounts to group (e.g., "Domestic airfare" + "International airfare");
•	A2.4.  The user clicks [Save Grouper] [E3] [E4];
•	A2.5.  The system validates required fields and name uniqueness (RN_PLA_008), persists the Grouper with the linked accounts and makes it available for rendering in the Budget module reports (RN_PLA_009);
•	A2.6.  The system writes the creation log to the audit trail (RN_PLA_004) and closes the modal, reactively updating the Groupers panel.

A3 — Edit Account Grouper
•	A3.1.  In the Groupers panel, the user clicks [Edit] on an existing Grouper;
•	A3.2.  The system loads the modal form with the Grouper's current data (Name and linked Accounts) in edit mode;
•	A3.3.  The user changes the Name and/or the selection of analytical accounts and clicks [Save Grouper] [E3] [E4];
•	A3.4.  The system validates, persists the changes and reactively updates the reports that reference this Grouper (RN_PLA_009). The change log is written to the audit trail (RN_PLA_004).

A4 — Delete Account Grouper
•	A4.1.  In the Groupers panel, the user clicks [Delete] on an existing Grouper;
•	A4.2.  The system displays a confirmation modal: "Do you want to delete the Grouper [Name]? This action will remove the corresponding subtotal from all linked reports." — [Confirm] and [Cancel] buttons;
•	A4.3.  The user confirms [E5];
•	A4.4.  The system removes the Grouper and its links, writes the deletion log (RN_PLA_004) and reactively updates the panel.

Exception Flows

E1 — Attempt to Manually Insert or Alter the Chart of Accounts
•	E1.1.  The user attempts to force the insertion of a new account or a nominal change to the description of an account imported from the ERP;
•	E1.2.  The backend security bus intercepts the invalid operation and aborts the transaction with immediate rollback (RN_PLA_001, RN_PLA_002);
•	E1.3.  The system displays the alert: "Operation Denied [ERROR LOCK]: The Chart of Accounts is governed exclusively by the Senior ERP. It is not permitted to insert, delete, or change account names directly in the SGO."


E2 — Detection of Orphan Analytical Accounts in the Synchronization Batch
•	E2.1.  During step 4 of the main flow, the validator identifies analytical accounts (Level 7) whose parent synthetic codes are missing from the ERP batch;
•	E2.2.  The SGO aborts the entire batch ingestion to preserve the referential integrity of the tree (RNF_PLA_REQ_004);
•	E2.3.  The system displays the alert: "Synchronization Error [ERROR LOCK]: Ingestion aborted. Analytical accounts without a corresponding parent synthetic account were detected. Check the structure in the Senior ERP."

E3 — Grouper Validation: required or insufficient fields
•	E3.1.  At step A2.4 or A3.3, the system identifies a blank Name or fewer than 2 selected analytical accounts (RN_PLA_008);
•	E3.2.  The system blocks the save and displays the inline alert: "The Grouper must have a filled-in Name and at least two selected analytical accounts.";
•	E3.3.  The system keeps the modal open with the entered data intact for immediate correction.

E4 — Duplicate Grouper Name
•	E4.1.  The system identifies that a Grouper with the same registered Name already exists;
•	E4.2.  The system blocks the save and displays the alert: "A Grouper with this name already exists. Use a unique name."

E5 — Block Deletion of a Referenced Grouper
•	E5.1.  The user confirms the deletion but the system identifies that the Grouper is referenced in active Disbursement Schedules or Proposals (RN_PLA_010);
•	E5.2.  The system aborts the deletion and displays the alert: "Deletion Blocked: This Grouper is referenced in active budget documents. Remove the references before deleting it."


Requirements 
Functional Requirements:
•	RF_PLA_REQ_001 — ERP Synchronization Trigger Component: The interface must provide an action button to trigger the synchronous update routine via the Senior ERP integration gateway.
•	RF_PLA_REQ_002 — Hiding Write Commands in the Chart of Accounts: Rendering [New], [Save Changes] or [Delete] buttons for accounts imported from the ERP is prohibited. The Chart of Accounts is Read-only for imported accounts.
•	RF_PLA_REQ_003 — Operational Parameterization Panel: Restricted interface for associating Nature Tags (Cost/OPEX, Investment/CAPEX) and Budget Traffic Light bands to already-imported accounts.
•	RF_PLA_REQ_004 — Elastic Tree Visualization: The screen must present the data in an expandable multi-level tree format of up to 7 levels, organizing synthetic and analytical nodes in ascending order.
•	RF_PLA_REQ_005 [NEW] — Account Groupers Panel: The interface must provide a dedicated panel for creating, editing and deleting SGO-exclusive Account Groupers, with a multiple selector of analytical accounts (Level 7) from the imported Chart of Accounts.
•	RF_PLA_REQ_006 [NEW] — Rendering Groupers in Reports: Active Groupers must be rendered as subtotal lines in the Disbursement Schedule (UC04.01) and other module budget reports, with a value calculated by the TotalizerService.
Non-Functional Requirements:
•	RNF_PLA_REQ_001 — Synchronization Response Time: Processing the ingestion, mapping and structuring of the tree (up to 5,000 accounts) must not exceed 5.0 seconds after the ERP payload is returned.
•	RNF_PLA_REQ_002 — Connection and Timeout Resilience: SeniorIntegrationController REST calls must have a maximum timeout of 10 seconds, triggering contingency mode on overflow.
•	RNF_PLA_REQ_003 — High-Performance Rendering: The multi-level accounting tree must support reactive expand and collapse maintaining a minimum rate of 60 FPS, without freezing the browser.
•	RNF_PLA_REQ_004 — Atomic Transactional Integrity (ACID): The synchronization routine must operate under absolute atomicity. Any failure in a single node causes an immediate rollback, preserving the previous base intact.
•	RNF_PLA_REQ_005 — Security and Segregation of Duties (RBAC): The synchronization backend endpoints must be shielded by encrypted authentication tokens. Common operational profiles cannot invoke the accounting load routine.
•	RNF_PLA_REQ_006 — Cent-Level Precision of Balances: The TotalizerService must use BigDecimal on the backend and numeric(18,2) in the database to compute aggregations, mitigating rounding errors.
•	RNF_PLA_REQ_007 — Concurrent Synchronization Control (Pessimistic Locking): The system applies a pessimistic lock during the load. If a second user attempts to trigger a new synchronization while a load is in progress, the action is rejected with an inline alert.

Business Rules 
•	RN_PLA_001 — Exclusive Governance of the Source (Shielded Origin Directive): Any account insertion, nomenclature change, or deletion of structural accounting records must occur in the Senior ERP master base. The SGO acts exclusively as a receiver — any direct manual change to these fields on screen is forbidden.
•	RN_PLA_002 — Absolute Block on Local Deletion and Modifications [ERROR LOCK]: The system applies a rigid lock at the database and endpoint level. Any attempt to bypass the interface to force deletion or nominal rewriting of imported accounts triggers an immediate rollback and generates a critical accounting governance violation alert.
•	RN_PLA_003 — Isolation of Entries at the Analytical Level (Leaf Node): The practical linking of operational expenses (Positions, Travel, Apportionments) occurs exclusively on Level 7 accounts (Analytical Account / Leaf Node). Higher levels (1 to 6) function strictly as reactive synthetic accumulators managed by the TotalizerService.
•	RN_PLA_004 — Accounting Synchronization Audit Log: Every update routine, bulk load, or Grouper creation/edit/deletion requires persisting an audit trail in HistoricodeOperacoes, capturing: user credentials, server date/time, IP, affected accounting code, previous state and updated state (JSON payload).
•	RN_PLA_005 — Tag Consistency and Hierarchical Inheritance: Operational parameterization tags (Cost/OPEX, Investment/CAPEX) inherit the nature of the parent node. If a Level 6 synthetic account is mapped as Investment (CAPEX), none of its child analytical accounts may be marked as Cost (OPEX).
•	RN_PLA_006 — Budget Traffic Light Color Alerts: Green (up to 70% consumption), Yellow (70% to 85%), Orange (85% to 95%) and Red (above 95% or budget ceiling overrun).

Account Grouper Rules

•	RN_PLA_007 [NEW] — Nature of the Account Grouper: Groupers are SGO-exclusive totalization entities that group analytical accounts from the ERP for display and subtotal purposes in budget reports. They are not part of the official Chart of Accounts, do not appear in the tree imported from the ERP, and do not interfere with the institution's accounting structure.
•	RN_PLA_008 [NEW] — Grouper Creation Restrictions: A Grouper must have: (a) a unique Name in the system context, (b) at least 2 associated analytical accounts (Level 7). Creating Groupers with a duplicate name or with only one analytical account is blocked [ERROR LOCK].
•	RN_PLA_009 [NEW] — Calculation via TotalizerService: The totalized value of a Grouper is dynamically calculated by the TotalizerService as the sum of the values of the associated analytical accounts, using BigDecimal and without rounding. The Grouper's value is Read-only — never editable by the user.
•	RN_PLA_010 [NEW] — Deletion Block for Active Reference [ERROR LOCK]: Deletion of a Grouper is blocked if it is referenced in active Disbursement Schedules, Expense Forecasts or Proposals. The user must remove the references before proceeding with the deletion.
•	RN_PLA_011 [NEW] — Multiple Participation of Analytical Accounts: The same analytical account (Level 7) can participate in multiple Groupers simultaneously (many-to-many relationship). Participating in a Grouper does not change the account's behavior in the ERP-imported Chart of Accounts.
