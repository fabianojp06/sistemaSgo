## [US-137] — CTCEA Salary Catalog (Persisted Rubi Grid)

**Module:** Registrations — Chart of Accounts / Positions and Salaries (external integration)
**Epic:** EP118/24
**Priority:** High
**Estimate:** M

**As a** GRH User,
**I want** the Salary Grid used when importing from Rubi to come from a real catalog loaded via
synchronization (the same pattern as the Unified Chart of Accounts, US-001), instead of values
generated by a hash at search time,
**So that** the Range/Level/Salary data shown when importing a Position reflects the CTCEA's
(Brazilian Organization for the Scientific and Technical Development of Airspace Control) real
salary table, auditable and traceable like any other external source in the system.

### Context and Business Rules

**Replaces the previous design:** US-132/ADR-045 (2026-08-14, implemented and in production)
modeled the Rubi import as a live search, with candidates generated by a deterministic hash from
the typed term (`CargoRubiFixtureProvider.buscarCargosPorTermo`). The same day, the user asked
for this flow to start working **exactly like the Chart of Accounts** (US-001): a catalog loaded
from a fixed file via a "Synchronize" button, no longer generated on the fly.

**Data source:** the CTCEA's real "Salary Table" report, structured as Class (F1-F7) × Level
(N1-N20/N22, variable per class) → Salary. Transcribed from 2 photos provided by the user
(2026-08-14); 2 anomalous values from Class F1 (N21=R$9.10, N22=R$8.91 — out of line with the
N19/N20 progression) were discarded by the user's decision — Class F1 goes up to N20, the same
ceiling already confirmed for the other classes (F2/F3/F4/F5 also go up to N20; F6/F7 confirmed
up to N20 in the photos received).

**Field mapping:**
- Class in the report (F1-F7) → catalog field `faixa`.
- Level in the report (N1-N20) → field `nivel`.
- Salary in the report → field `salario`.
- **`cargoMercado` and `cargoCtcea` (position names) are NOT in this report** — the document only
  has Class/Level/Salary, with no position name associated. They remain **nullable**, populated
  only when the user provides a 2nd source relating Class/Level to position names (out of scope
  for this US). Until then, the catalog is a "mute" grid — just numbers, with no position
  identification.

**Name of the "CTCEA Position" field:** it is not a specific position — it is the identifier of
the source/classification the data comes from (the acronym of the organization whose report
feeds the catalog), a conceptual parallel to "Market Position" (which would come from another
source/survey). The two position names share the same Range/Level/Salary grid, but are labeled
differently according to the source.

### Acceptance Criteria

**Scenario 1 — Initial synchronization loads the full grid**
```gherkin
Given the CTCEA Salary Grid catalog is empty
When the administrator user clicks "Synchronize" on the corresponding screen
Then the system loads every Range (F1-F7) × Level × Salary combination from the embedded fixed file
And cargoMercado and cargoCtcea remain null on every row (the 2nd source has not been provided yet)
And an audit record is written (same pattern as SYNC_PLANO_CONTAS)
```

**Scenario 2 — A new synchronization updates without duplicating**
```gherkin
Given the Salary Grid has already been synchronized once
When the user synchronizes again (e.g., the source file was updated with new salary values)
Then existing rows (same Range+Level) are updated via upsert, not duplicated
And cargoMercado/cargoCtcea values already filled in manually (if a 2nd source has already been loaded) are preserved,
  the same pattern as Scenario 2 of US-001 (preserving local configuration when re-importing external data)
```

**Scenario 3 — Importing a Position searches the catalog, no longer generates by hash**
```gherkin
Given the CTCEA Salary Grid is synchronized
When the user opens "Import from Rubi" on the Position and searches by Range/Level (or by term, if cargoMercado/
  cargoCtcea are already filled in)
Then the system returns candidates coming from the persisted catalog (no longer generated by hash)
And when a candidate is selected, the fields are filled in as already defined in US-132/ADR-045
  (nomeCargoMercado, tabSalCodigo/Descricao, faixaCodigo/Descricao, nivelCodigo/Descricao, salarioReal)
```

**Scenario 4 — Search with cargoMercado/cargoCtcea not yet filled in**
```gherkin
Given the catalog has rows with cargoMercado/cargoCtcea still null (the 2nd source has not arrived)
When the user searches by Range/Level directly (not by position name, which does not exist yet)
Then the system returns the candidates for that Range/Level, with nomeCargoMercado empty/placeholder
  until the 2nd source is loaded
```

### Technical Impact (guidance for dev)

| Aspect | Detail |
|---|---|
| New table | `GradeSalarialCtcea` (or an equivalent name defined by the Tech Lead): `tenantId`, `faixa` (F1-F7), `nivel` (N1-N20), `salario` (Decimal 15,2), `cargoMercado` (String?), `cargoCtcea` (String?), `syncedAt`. Unique on `(tenantId, faixa, nivel)`. |
| Provider/Loader | Same pattern as `PlanoContasArquivoProvider`/`PlanoContasBulkLoader` (US-001) — an embedded fixed file (`.ts` with the transcribed data), bulk upsert. **Tech Lead's decision:** reuse this exact pattern or design a dedicated loader (there is no parent/child hierarchy here as there is in the Chart of Accounts). |
| `ImportarCargoRubiUseCase`/`CargoRubiFixtureProvider` | Search starts querying `GradeSalarialCtcea` instead of generating by hash. **Tech Lead's decision:** migrate 100% now (remove the hash fixture) or keep both coexisting until the 2nd source (position names) arrives. |
| Migration | New table, additive, no impact on existing Position data. |
| Audit | Reuse `SYNC_PLANO_CONTAS` as a model — a new event type (e.g., `SYNC_GRADE_SALARIAL_CTCEA`) for `HistoricoOperacao`. |

### Dependencies

- **Tech Lead ADR** — blocking: the exact table name, the decision of 100% migration vs.
  temporary coexistence with the hash fixture, and whether the Chart of Accounts loader is
  reused or not.
- **2nd data source (position names by Range/Level)** — does not block this US (the catalog is
  born with `cargoMercado`/`cargoCtcea` null), but is a prerequisite for the catalog to be
  "complete" in the sense of already having searchable position names.
